## How to read this document

Every item is one row in one category. Categories, in the order a release should resolve them:

| Category | Meaning |
|---|---|
| **BLOCKER** | So severe that continuing release-track work without addressing it would be irresponsible. None found in this audit -- see [Summary](#summary). |
| **REQUIRED BEFORE RC** | Must be resolved before cutting `1.0.0rc1`. An RC exists to be evaluated as release-shaped; these items are things that would make the RC itself misrepresent the project's actual state or safety envelope. |
| **REQUIRED BEFORE FINAL** | Can be resolved during the RC evaluation window (between `1.0.0rc1` and `1.0.0` final), including anything that depends on RC feedback or a real manual PyMOL session against the RC build itself. |
| **ACCEPTED LIMITATION** | Known, deliberate, already-documented scope boundary. Does not block 1.0.0. Listed here so the 1.0 audit trail is explicit about what was consciously accepted, not silently missed. |
| **POST-1.0** | Explicitly deferred past 1.0.0 -- either low-value now or dependent on real-world 1.0 usage feedback. |

Each item states: description, evidence (file:line or doc citation), affected files/components,
proposed resolution, validation method, owner/action type, and status.

  since the last audit and already regression-gated** by `tests/test_contract_freeze.py`. The real
  risk surface for 1.0 is concentrated in **three places**: (1) one specific async error-handling
  gap in the PDBTM-cache worker, (2) documentation currency/completeness (upgrade guide, status
  vocabulary, contract-freeze provenance), and (3) **the complete absence of any manual acceptance
  evidence for the v0.9.0 GUI redesign or an v0.8.0-to-current upgrade**, which is a testing gap,
  not a code defect.
- **Direct 1.0.0rc1 vs. public 0.9.0 recommendation: a public 0.9.0 prerelease is still required**
  -- see [1.0.0_plan.md §Phase D](1.0.0_plan.md#phase-d) for the full rationale. In short: PR #37
  (substantial GUI restructuring) and PR #38 (scientific-foundation README) have never been
  manually validated against real PyMOL, and no upgrade path from the only published prerelease
  (v0.8.0) has ever been exercised, automated or manual. Every prior version in this project's
  history published its own prerelease with a completed manual-acceptance record before the next
  phase of work began; skipping that discipline for the single largest UI change in the project's
  history, under the highest-stakes version label it has ever used, is not justified by the
  evidence gathered here.

## 3. Findings

### REQUIRED BEFORE RC

**R-1. `CSV_FIELDS` has no contract-freeze regression test.**
Every other frozen shape in this project (commands, batch contracts, schemas, cache format, status
vocab subset, `__all__` -- see R-9) is pinned by an explicit test in `tests/test_contract_freeze.py`
that fails on silent drift. `CSV_FIELDS = ["model", "chain", "resi", "resn", "classification",
"severity", "reason", "z"]` (`membrane_vqc/report.py:62`) is not. A future refactor could reorder or
rename a column with no test failure.
- Affected: `membrane_vqc/report.py:62`, `tests/test_contract_freeze.py`.
- Resolution: add `FROZEN_CSV_FIELDS = (...)` + an assertion test, mirroring the existing pattern
  for `STATUSES`/`BATCH_STATES` in the same file.
- Validation: new unit test passes; deliberately mutate `CSV_FIELDS` locally and confirm the test
  fails (then revert).
- Owner/action: engineering, small code+test change.
- Status: not started.

**R-2. `docs/status_vocabulary.md` is not exhaustive, contradicting its own stated completeness claim.**
`batch_result_browser.py` and `batch_gui.py` raise several real, stable-looking codes not listed in
the doc: `REPORT_JSON_INVALID`, `REPORT_SCHEMA_MISMATCH`, `REPORT_RESULT_CONTRADICTION`,
`OUTPUT_INVENTORY_INVALID`, `OUTPUT_TOTAL_LIMIT_EXCEEDED` (`batch_result_browser.py:79,84,93,95,198,
202,218,229`), plus several GUI-only codes (`RESULT_BUNDLE_INVALID`, `RESULT_MANIFEST_UNAVAILABLE`,
`RESULT_MANIFEST_CHANGED`, `OUTPUT_DIRECTORY_UNAVAILABLE`, `PLAN_INVALID`, `BATCH_START_FAILED`,
`BATCH_EXECUTION_FAILED`, `BATCH_FINALIZE_FAILED`, `batch_gui.py:389,483,514,542,724,826,842,857`).
`status_vocabulary.md`'s own introduction states undocumented terms are not literals this project
defines -- currently false.
- Affected: `docs/status_vocabulary.md`, `membrane_vqc/batch_result_browser.py`, `membrane_vqc/batch_gui.py`.
- Resolution: add a new subsection enumerating these codes with the same rigor as the existing
  cache/provider error-code table.
- Validation: extend `tests/test_documentation_consistency.py`'s existing
  `test_status_vocabulary_matches_*` pattern to cover this new subsection.
- Owner/action: documentation, small-edit.
- Status: not started.

**R-3. PDBTM-cache async worker can let an untyped exception escape uncaught to the Qt event loop.**
This is the single most concrete "a raw traceback could reach the user" finding in the whole audit,
and it is architecturally isolated -- every other async/worker path in this codebase already
handles it correctly, which was independently re-verified during this audit (not just taken from
agent output):
- `membrane_vqc/comparison_worker.py:126,170,175-178` -- `ComparisonWorkerOrchestrator.compare()`
  docstring literally states *"Return a result or a stable safe failure; never raise raw local
  diagnostics"*, and has a genuine `except Exception:` catch-all converting anything unexpected into
  `ComparisonWorkerFailure("COMPARISON_FAILED", ...)`.
- `membrane_vqc/batch_executor.py` -- 8 separate `except Exception` sites guarding per-job execution.
- `membrane_vqc/pdbtm_worker.py:87,104,117,124` (`PdbtmWorkerOrchestrator.inspect/fetch/
  use_cached_pair/clear`) -- **zero `except` clauses anywhere in the file** (independently
  reconfirmed by direct grep during this audit).
- `membrane_vqc/pdbtm_gui_worker.py:91-123` (`_run_inspect`/`_run_fetch`/`_run_use_cached`/`_run_clear`)
  -- each catches **only `Stage4BError`**, no catch-all. These run on a background `QThread` via a
  Qt queued-connection slot; an exception escaping a Qt slot has no `_show_error` path (that path
  only exists on `gui.py`'s synchronous `_execute` wrapper used by workflows 1-3 and the *synchronous*
  half of the cache workflow, e.g. Run QC against an already-selected cache snapshot -- not the
  Fetch/Inspect/Use-cached-pair/Clear buttons themselves).
- `tests/test_pdbtm_gui_worker.py` only has `test_request_inspect_failure_becomes_worker_failure` and
  `test_request_use_cached_failure_becomes_worker_failure`, both injecting `Stage4BError` specifically
  -- no test injects a generic exception to observe what actually happens.
- Affected: `membrane_vqc/pdbtm_worker.py`, `membrane_vqc/pdbtm_gui_worker.py`.
- Resolution: mirror `comparison_worker.py`'s exact pattern -- wrap each `PdbtmWorkerOrchestrator`
  method body (or the four `_run_*` call sites) in `except Exception: return
  <SafeFailure-equivalent>`, converting to the existing `WorkerFailure`/`Stage4BError`-shaped result
  the GUI already knows how to render, rather than letting anything else propagate.
- Validation: new unit test injecting a plain `RuntimeError` from a fake orchestrator into each of
  the four `_run_*` methods, asserting a safe failure result is emitted, not a raised exception.
- Owner/action: engineering, minimal and precedented code change (Phase B).
- Status: not started.

**A-5. Session-only batch history and no cache auto-migration remain permanent, documented

**A-6. Two independently-defined record-ID regexes** (`pdbtm_provider.py`'s case-insensitive

## 5. Versioning and backward-compatibility policy for 1.x

`docs/versioning_policy.md` already exists and, per this audit, is materially complete and accurate
against current code (its deprecation process, additive-only rule for status/error codes, and
"what requires a 2.0" framing all check out). This section states the concrete 1.x commitments this
readiness programme recommends, extending that existing policy rather than replacing it:

- **Frozen for the entire 1.x series** (breaking change requires 2.0): the 11 public PyMOL command
  signatures; `mvqc-batch-plan-1.0`/`mvqc-batch-result-1.0` contract identifiers and the 5 batch
  modes; report schemas 1.0-1.5 (a new schema version may be *added* for new optional evidence, but
  1.0-1.5 never change shape); the `cache-v1` on-disk format; `CSV_FIELDS` order and names (once
  R-1 lands); the documented status/outcome vocabulary (once R-2 lands, the *complete* vocabulary,
  not just the currently-documented subset); the 5-name public Python API surface (once R-9 pins
  it); output/manifest filenames and atomic-publish semantics; `MVQC_CACHE_DIR` as the one
  environment variable.
- **Explicitly not frozen, may change within 1.x without a major bump**: GUI layout, wording, and
  mode-string literals; comparison thresholds/bands (5°/2Å/2Å) and any other scientific
  review-heuristic value; internal module structure not listed above; `qc.LAST_REPORT` and other
  internal-only state.
- **Additive-only changes allowed within 1.x** (minor version bump, no deprecation needed): new
  optional report/plan fields; new status/error codes (provided existing ones never change meaning);
  new orientation-source modes; new optional CLI flags with safe defaults.
- **Deprecation process** (already defined in `versioning_policy.md`, restated as the 1.x
  commitment): a frozen interface may only be changed by (1) introducing the new behavior alongside
  the old, (2) marking the old path deprecated with a documented removal-eligible version, (3)
  keeping both for at least one full minor release cycle, (4) removing only in a version that itself
  documents the removal in `CHANGELOG.md` and `known_limitations.md`.
- **Conditions that require a 2.0, not a 1.x release**: removing or renaming any frozen PyMOL
  command or parameter; changing the meaning (not just adding to) any status/error literal; breaking
  batch-plan or report-schema backward compatibility (old plans/reports no longer parse); changing
  the cache format in a way that invalidates existing cache-v1 snapshots without a migration path;
  changing the core signed-distance/classification mathematics in a way that reclassifies previously
  `core` points as `interface`/`outside` or vice versa for the same input.
